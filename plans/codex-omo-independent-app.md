## 合同冻结

- 输入：用户从 App 内照片选择器或后续 Share Extension 提交的一张截图。
- 输出：可恢复的截图任务；成功时关联 canonical 记忆卡，失败时保留明确原因和重试动作。
- Schema / API：截图任务拥有稳定 task ID、截图指纹、状态、失败语义、重试次数和最终 card ID；客户端不再依赖单次同步长请求表示整个生命周期。
- 兼容要求：保留现有 `/api/sources/image-flow` 供旧构建使用；现有卡片和 assessment 行为不回归。
- 失败语义：任何任务必须结束为 succeeded 或 failed，或在重启后继续呈现 accepted / processing；不允许静默消失。

## 1. 已证实的结论

当前版本没有删除抽卡、刮刮乐或自评条。它们仍在当前代码中，并能在带有可复习卡片的数据状态下运行。

用户在 TestFlight 中遇到的主问题是：真实截图生成失败后，App 一直停留在“没有任何可复习卡”的空状态，因此抽卡、刮开和自评都不可达；同时空状态本身又错误地把收藏夹画成不可点击图片，并在上传期间禁用加号，最终形成“页面看起来有入口，但几乎全部不能点”的体验。

### 1.1 证据

1. 当前 Debug 构建注入开发卡片后，首页的 IP、收藏夹、上传均可点击。
2. 点击 IP 后，当前构建能进入四层卡组；强制揭示状态下，自评 Slider、详情、收藏夹、上传入口均存在。
3. 当前 `RecallRatingSlider.swift` 与上次成功验收提交 `cfa7b02` 无差异。
4. 当前刮开组件仍保留局部遮罩、80% 阈值和完全揭示逻辑；相对上次成功提交只新增了“揭示后才能打开完整上下文”的限制。
5. 上次成功验收明确使用 `OMO_DEMO_MODE=1` 和临时 Fixture 数据，不是 TestFlight 的真实空库上传链路。
6. Omo staging 日志中，用户此前的 `POST /api/sources/image-flow` 在约 60.9 秒后返回 504；卡片没有保存。
7. 本次用产品提供的真实截图再次请求 staging，18.7 秒成功生成卡片，说明服务不是必然失败，而是耗时与可靠性存在波动。
8. 当前 37 个 XCTest 全部通过，但没有 UI Test target，也没有慢请求、504、上传期间点击、杀进程恢复等测试。

## 2. 问题清单与原因

### P0-1 空库收藏夹不可点击

- 表现：用户没有卡片时，首页收藏夹看起来像入口，但点击无响应。
- 直接原因：空库分支使用普通 `Image("FirstLaunchFolder")`；只有有卡分支才使用 `Button`。
- 为什么以前没发现：成功 Simulator 演示通常先注入了卡片，因此进入的是有卡分支。
- 违反 PRD：收藏夹在空库、处理中和有卡时都必须可用。

### P0-2 上传期间加号被全局禁用

- 表现：选择第一张截图后，加号变灰且不能再次点击。
- 直接原因：单一全局布尔值 `store.isCreating` 驱动 `.disabled(isCreating)`。
- 深层原因：前端把“一个上传任务正在处理”错误建模成“整个产品正在创建”。
- 违反 PRD：处理一张截图时，加号、收藏夹、菜单仍可用。

### P0-3 第一张截图请求是同步、长耗时且不可恢复的

- 表现：页面长时间显示“正在整理”；请求 504 后没有卡片；用户无法判断是处理、卡死还是失败。
- 直接原因：客户端发起一次同步 `POST /api/sources/image-flow`，等待模型、溯源和数据库保存全部完成后才得到响应。
- 服务侧证据：同一接口一次约 18.7 秒成功，另一次约 60.9 秒被网关以 504 终止。
- 深层原因：耗时 AI 工作没有独立任务身份、持久状态和轮询接口。

### P0-4 处理状态只存在内存，杀 App 后静默消失

- 表现：后台杀掉 App 再打开，“正在处理”消失，卡片也不存在。
- 直接原因：`isCreating` 只是 `OmoStore` 的内存状态；截图数据和处理任务均未持久化。
- 深层原因：前后端都没有“已接收 / 处理中 / 成功 / 失败”的任务合同。
- 违反 PRD：重新启动后必须恢复真实任务状态，不能静默丢失。

### P0-5 生成失败没有可见、可操作的恢复路径

- 表现：空库时最多出现一条短错误文字；没有针对该截图的重试项。已有卡时，从首页上传失败甚至看不到错误。
- 直接原因：失败只写入全局 `store.message`；首页有卡分支不渲染 `statusText`，且没有处理任务模型或重试按钮。
- 深层原因：错误被当成瞬时 Toast，而不是上传任务的终态。

### P0-6 IP 的可达性完全依赖成功生成卡片

- 表现：真实上传失败后，IP 永远不能进入抽卡；用户主观感受是“IP 也坏了”。
- 直接原因：只有 `dueCards` 非空时 IP 才是 Button；这是合理前置条件，但页面没有解释“当前没有可抽卡片”的真实状态。
- 判断：不是刮刮乐代码故障，而是上游没有产生可复习卡。

### P0-7 知识库没有处理中/失败任务

- 表现：用户无法去收藏夹确认截图是否仍在处理，也无法从失败项重试。
- 直接原因：知识库只接收 `[MemoryCard]`，没有上传任务列表。
- 深层原因：数据模型只有最终卡片，没有生成生命周期。

### P1-1 App 启动加载失败缺少明确状态与重试

- 表现：首次加载失败时可能先显示空库引导；没有独立“加载失败 + 重试”状态。
- 直接原因：`isLoading` 和 `message` 没有形成首页状态机，`cards.isEmpty` 被同时用来表示“真实空库”和“尚未加载成功”。

### P1-2 两套上传界面行为不一致

- 表现：首页加号直接打开照片选择器；知识库加号先打开“添加内容”Sheet，再打开照片选择器，等待文案和失败呈现也不同。
- 直接原因：首页和知识库分别实现了截图读取、许可和生成流程。
- 风险：同一动作在不同入口产生不同状态和错误恢复方式，后续修复容易只覆盖一处。

### P1-3 通知卡叠加时没有保留持久首页入口

- 表现：通知卡以高层级覆盖首页；与普通复习轮次不同，它没有在同一层重新放置收藏夹和加号。
- 直接原因：通知 `RecallRoundView` 单独以 `zIndex(20)` 叠加，持久入口位于其下方。
- 违反 PRD：通知卡状态下菜单、收藏夹、加号仍应可用。

### P1-4 处理文案伪装成精确进度

- 表现：知识库上传 Sheet 显示“正在识别标题并通过 TickHub 核对来源”，但前端并不知道后端当前进行到哪一步。
- 直接原因：同步接口不返回阶段事件，UI 使用固定文案猜测阶段。
- 风险：卡住时用户以为某个阶段仍在工作，实际请求可能已经超时。

### P1-5 没有并行上传任务模型

- 表现：产品要求处理一张时仍可继续上传，但当前 Store 只能容纳一个 `isCreating`。
- 直接原因：缺少基于 task ID 的任务数组和单任务状态。

### P1-6 Share Extension 尚未实现

- 表现：PRD 约定的主要日常入口——系统分享截图到 Omo——当前工程不存在对应 target。
- 证据：Xcode 工程只有 `Omo` 与 `OmoTests` 两个 target。
- 判断：这是 MVP 功能缺口，不是本次“首页死掉”的直接原因，但应在 TestFlight 核心流程完成前明确排期。

### P1-7 自动化验收只覆盖状态逻辑，没有覆盖真实点击链路

- 表现：37 个 XCTest 全部通过，真机仍出现核心入口不可用。
- 直接原因：项目没有 UI Test target；创建卡测试使用立即返回的 Stub。
- 深层原因：把 Store 单元测试、Fixture 截图和历史 Bundle 的结果当成最终构建交互验收。

### P2-1 空库/无到期卡时 IP 缺少明确的不可用反馈

- 表现：IP 保留视觉，但没有按钮语义；用户可能仍认为它应该能点。
- 处理原则：不增加抢注意力的常驻文字；通过动画状态、触控反馈或上下文引导，让“现在不能抽”可理解。
- 备注：具体 IP 形象和动画仍不在本轮决定。

## 3. 为什么看起来像“突然什么都没了”

这不是一次单点 UI 删除，而是两个条件叠加：

1. 以前成功的 Simulator 验收预置了卡片，直接进入“有卡”分支；因此 IP、收藏夹、卡组、刮刮乐和自评都能出现。
2. TestFlight 从真实空库开始，第一张截图又在真实 AI 请求中超时；因此 App 一直停在有缺陷的“空库/处理中”分支。

空库分支从上次成功提交起就已经存在“收藏夹只是图片、加号处理时禁用”的问题。它不是这几天才被删坏，而是之前的验收数据没有触达这个分支。当前版本新增的 AI 许可和通知逻辑没有删除刮刮乐或自评条。

## 4. 推荐修复设计

### 4.1 第一原则

用户选择截图后，产品首先必须可靠地承认“我已经接住了这张截图”，然后 AI 才可以慢慢处理。不能让一次持续几十秒的网络请求同时承担“接收任务”和“生成完成”两种职责。

### 4.2 最小可靠任务模型

每张截图形成一个独立 `ScreenshotJob`：

```text
localPreparing
→ accepted
→ processing
→ succeeded(cardID)
或 failed(retryable, message)
```

每个任务至少保存：task ID、截图指纹、创建时间、状态、失败原因、重试次数、最终 card ID。重复截图使用同一幂等键，避免重复卡。

### 4.3 前后端合同

推荐采用轻量异步任务，而不是继续延长同步超时：

1. `POST /api/screenshot-jobs` 快速接收截图并返回 `202 + job`。
2. Railway worker 在后台执行模型、溯源和保存。
3. `GET /api/screenshot-jobs` 返回当前设备全部未完成与近期失败任务。
4. `GET /api/screenshot-jobs/:id` 返回单任务状态。
5. `POST /api/screenshot-jobs/:id/retry` 重试同一任务。
6. 成功后任务关联 canonical `cardID`；卡片 ID 或幂等键继续以截图指纹保证去重。

如果为控制 MVP 复杂度需要分两步，第一步可以先在 iOS 本地持久化待上传截图并在重启后幂等重试；但这只能作为过渡方案，不能解决服务处理超过 Railway 请求时限的问题。因此最终仍推荐异步任务合同。

### 4.4 首页与知识库表现

- 空库收藏夹始终是 Button，可进入空知识库。
- 加号不因其他任务处理中而禁用；只在系统选择器或许可弹窗自身活动时防重复触发。
- 首页显示轻量任务摘要，不覆盖三个核心入口。
- 知识库把处理中和失败项放在完整卡片之前；失败项提供重试。
- IP 是否可抽只看 `dueCards`，与其他截图任务无关。
- 有卡首页的上传失败必须有可见反馈。
- App 启动先区分 loading、loadedEmpty、loadedWithCards、loadFailed，不把加载失败误当空库。
- 通知卡叠加时，收藏夹和加号保持在可点击层。
- 两个上传入口共用一个 Upload Coordinator，不再复制流程。

## 5. 实施顺序

### 阶段 A：先建立失败测试

1. 新增 `OmoUITests` target。
2. 为首页建立可控 Fixture：空库、处理中、有卡、加载失败、生成失败。
3. 添加 UI 测试：空库收藏夹可点；处理中菜单/收藏夹/加号可点；有旧卡时 IP 可点。
4. 添加 Store 测试：慢请求不锁入口；失败进入 failed；重启恢复；重试复用 task ID。
5. 添加后端合同测试：202 接收、状态轮询、超时失败、幂等重试、服务重启恢复。

### 阶段 B：修复 P0 入口和状态模型

1. 把空库收藏夹改为与有卡状态共用的持久 Button。
2. 用 `[ScreenshotJob]` 替换全局 `isCreating`。
3. 抽出统一 Upload Coordinator，首页和知识库共用。
4. 首页与知识库增加 processing / failed / retry 展示。
5. 增加独立 loading / loadFailed 状态和重试。
6. 处理任务与卡片状态持久化并支持 App 重启恢复。

### 阶段 C：接入异步 staging 合同

1. 后端增加持久任务表和异步执行器。
2. iOS 改为快速接收 + 轮询，不再等待同步 image-flow。
3. 用截图指纹实现幂等和重复提交归并。
4. Railway 只部署 staging，验证服务重启、模型超时和数据库恢复。

### 阶段 D：修复次级交互缺口

1. 通知卡叠层保留收藏夹、上传和菜单的可点击性。
2. 删除假阶段文案，改成由真实任务状态驱动。
3. 为无可复习卡的 IP 提供不抢注意力的状态反馈。
4. 建立 Share Extension target，复用同一任务接收合同。

### 阶段 E：完整验收

1. 使用本次提供的截图验证真实 staging 成功、超时、失败和重试。
2. Simulator 逐项实际点击空库、处理中、有卡、复习、通知、知识库。
3. 验证 79%/80% 刮开、自评取消、三个自评节点、失败重试。
4. 处理中切后台、杀 App、重新打开，确认任务不消失。
5. 用与 TestFlight 相同的 Release Archive 在真机复测，不沿用 Debug Fixture 证据。
6. 每个关键状态保存截图或录屏，并单列未验证项。

## 6. 本轮明确不重写的部分

- 当前刮刮乐的局部遮罩与 80% 阈值。
- 当前自评条的完整渐变、固定色箭头、取消区和三个正式节点。
- 当前四层卡组和回顾中保留收藏夹/上传的正常路径。
- 当前知识卡揭示后的字重与强调色逻辑。

这些部分只有在真实交互验收发现具体失败后才做针对性修改，避免把上游不可达误诊为组件被删除。

## 7. 完成标准

只有同时满足以下条件，才可以再次声明“核心前端交互已修复”：

1. 空库、处理中、有卡三个状态的核心入口逐个真实点击通过。
2. 首张真实截图能结束为成功或明确失败，并能重试。
3. 处理中杀 App 后状态可恢复。
4. 成功卡在首页、知识库和重启后都存在，并能进入抽卡、刮开、自评。
5. 自动测试覆盖慢请求、504、重启恢复和按钮可点击性。
6. 最终 TestFlight Release 真机通过同一份 PRD 验收。
